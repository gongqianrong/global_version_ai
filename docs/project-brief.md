## 1. Project Vision & Problem Statement

### Problem

东南亚（尤其是越南）消费者对日本商品有强烈的购买需求，但面临以下障碍：

- **语言壁垒**：日本电商平台（Mercari、Rakuma、TOBU、SuperDelivery 等）均为日语界面，东南亚用户难以直接使用
- **购买流程复杂**：跨境代购涉及汇率换算、国际物流、关税处理等环节，普通消费者难以独立完成
- **信任缺失**：通过个人代购存在诈骗风险，且服务质量不稳定
- **平台分散**：日本商品分散在多个电商平台，用户需要逐一注册和搜索

### Vision

Rakutao 将多个日本电商平台的商品聚合为统一的代购服务平台，以 Rakutao 自有品牌呈现给东南亚用户。用户无需了解底层商品来源，即可在一个 App 中完成搜索、浏览、下单、支付和物流追踪的全流程，享受一站式日本商品代购体验。

### Strategic Logic: 为什么是这个产品形态

> 以下从设计决策中反向推导其背后的核心商业逻辑，理解"为什么这样做"比"做什么"更重要。

**代购的本质是信息差变现，而非简单的买卖。**

东南亚用户有购买力，日本平台有商品，但两者之间隔着语言、支付、物流三道墙。Rakutao 并不生产商品，也不持有库存——它经营的是一种**跨境信息不对称的消化服务**。用户为"能买到"而非"商品本身"付费。这决定了平台的一切设计决策都服务于一个目标：**让信息差对用户不可见，同时让信息差对平台持续可变现**。

**聚合不是功能，是护城河。**

单一来源（只接 Mercari）的代购没有壁垒——任何人都能做到。但同时聚合 Mercari、Rakuma、TOBU、SuperDelivery、BEAMS 等多平台数据，并以统一体验呈现，这件事的技术复杂度和运营成本构成了天然壁垒。用户一旦习惯"搜一次出所有平台的结果"，就不会再回到逐平台搜索的原始状态。**聚合本身就是产品，而不是产品的一个功能。**

## 1.5 Design Decisions: 核心设计决策推演

以下逐条解释关键设计决策背后的深层原因。

### 为什么隐藏来源平台？

表面原因是"强化品牌"，但本质是**保护商业模型的存续条件**。

如果用户知道某件商品来自 Mercari，理性用户的下一步就是自己去 Mercari 购买，Rakutao 随即变得多余。隐藏来源并非欺骗——而是将"多平台聚合 + 翻译 + 代购 + 物流"打包为一个不可拆分的服务。用户购买的是这个完整的服务，而非某件 Mercari 商品。这与酒店比价平台不同（Booking.com 会告诉你酒店名称），因为代购模式中用户无法绕过中间商直接完成交易。信息遮蔽是合理的，因为即使用户知道来源，他们仍然无法独立完成跨境购买。

设计图中的佐证：首页商品卡片上不显示平台 logo；商品详情页的卖家信息模块隐藏源平台品牌。

### 为什么搜索和指定购买是两个并行通道？

搜索解决的是"我想要某类东西"——用户有模糊意图，平台帮助发现。
指定购买解决的是"我就要这个东西"——用户已经明确知道目标。

两者缺一不可，因为它们覆盖了用户决策链条的两个极端。更关键的是，**指定购买将整个互联网变成了 Rakutao 的商品目录**。用户在 Instagram 看到一个日本商品推荐、在 YouTube 看到一个开箱视频、在朋友聊天中收到一个链接——这些场景中用户不需要在 Rakutao 内搜索，只需把链接粘贴进来。这意味着 Rakutao 的流量入口不限于自身 App 内部，而是扩展到了整个社交网络。

设计图中的佐证：底部导航 5 个 Tab 中，Order Link 与 Home、Cart 平级——它不是一个隐藏的次要功能，而是与主流浏览并列的一级入口。

### 为什么是钱包系统而不是直接支付？

直接支付（每笔订单独立付款）在代购场景中有三个致命问题：
1. **东南亚支付碎片化**——越南流行银行转账和 MoMo，台湾用信用卡和 LINE Pay，没有统一支付方式。钱包把"如何充钱进来"和"如何花钱"解耦了：充值环节适配各国支付方式，消费环节统一使用钱包余额。
2. **代购天然有时间差**——用户下单后，平台需要人工确认价格、在源平台代购、等待卖家发货，可能还需要补差价。如果没有钱包，每个环节都要触发一次支付，用户体验碎片化。钱包预充值让整个链条只有一个支付动作。
3. **资金沉淀创造粘性**——钱包里有余额的用户不会轻易离开平台。这不是"锁客"手段，而是降低了用户每次购物的决策摩擦。

设计图中的佐证：钱包页顶部突出显示"残高(円)" + "チャージ"按钮，余额是最显眼的信息；钱包整合了订单、运单、流水三大模块，是用户的"财务控制中心"而非简单的支付工具。

### 为什么价格只显示 JPY？

如果平台以越南盾或台币标价，就意味着平台承诺了一个汇率。汇率每分钟都在变，从用户下单到平台实际在日本付款可能隔了数小时甚至数天。这段时间内的汇率波动，要么平台吃亏（汇率不利时），要么用户投诉（发现实际扣款更多时）。

**JPY 标价将汇率风险转嫁为用户的已知变量**——用户充值时就已经按当时汇率换了 JPY 进入钱包，之后所有消费都在 JPY 体系内完成。平台避免了汇率对赌，用户也获得了价格确定性（"这个包 23600 日元就是 23600 日元"）。

设计图中的佐证：商品详情页价格区域主显示 "JPY 23600"（红色粗体），汇率仅作为参考小字显示（灰色）——信息层级上，JPY 价格是确定承诺，汇率是辅助信息。

### 为什么以日本法人主体上架、默认日语？

Rakutao 的目标用户不是日本人（日本人不需要代购日本商品），但 App 默认语言是日语。这看似矛盾，实则是**法律合规与信任构建的双重策略**：

1. **法律层面**：以日本法人上架、默认日语，使 App 在应用商店审核中被视为一款日本本地 App。这降低了跨境电商的审核复杂度，避免各国对"外国购物 App"的额外监管。
2. **信任层面**：对东南亚消费者而言，"一家日本公司卖日本商品"的信任度远高于"一家外国公司帮你从日本买东西"。日语默认不是为日本用户设计的——它是一面旗帜，告诉用户"这是一个日本原产的服务"。

设计图中的佐证：启动页后第一个交互就是语言选择页，日本語预选高亮；平台选择页的描述文案使用日语。

### 为什么屏蔽中国大陆？

中国大陆拥有成熟的跨境电商生态（淘宝全球购、京东国际、小红书等），日本代购在国内已是红海市场。进入这个市场意味着与巨头正面竞争，且面对中国严格的跨境电商监管和ICP备案要求。

屏蔽大陆不是被动的法律回避，而是**主动的战略聚焦**：把资源集中在东南亚这个代购服务供给不足、需求正在增长的市场。越南、台湾等地没有成熟的日本代购平台，Rakutao 在这些市场是先行者而非追随者。

### 为什么收藏夹要支持"关注卖家"？

商品收藏解决的是"我对这个东西感兴趣"。但在 Mercari 这样的 C2C 平台上，优质卖家往往持续上架同类优质商品（比如一个专门卖 vintage 包的卖家）。**关注卖家将一次性交易转化为持续关系**——用户不再是"买完就走"，而是"定期回来看看这个卖家上了什么新货"。

这在没有 Push 通知、没有优惠券、没有运营位的 MVP 阶段尤为关键——关注卖家是平台唯一的**用户自驱动回访机制**。它不需要运营团队推送内容，用户自己会回来。

设计图中的佐证：收藏夹页提供 "My Favorites" 和 "Follow Seller" 两个平级 Tab。

### 为什么购物车要强调价格变动？

代购场景中，从"加入购物车"到"实际付款"之间，源平台的商品价格可能已经变化（C2C 卖家调价、限时促销结束、汇率波动等）。如果用户按旧价格的预期付款，发现实际扣款不同，这就是一个客诉。

**价格变动提示把"可能的纠纷"前置为"已知的信息"**——用户在付款前就已经看到价格变了，这是他做出"继续购买"还是"放弃"决策的依据。这不是功能，这是**信任维护机制**。

设计图中的佐证：MVP 功能需求明确写道"购物车需要显示价格变动"；购物车卡片组件设计了价格区域的突出显示位置。

### 为什么用 LLM 翻译而不是人工翻译？

Rakutao 的商品目录不是自有数据——它是从多个平台实时抓取的。Mercari 上每天有数十万件新商品上架，Rakuma 和其他平台同理。这些商品的生命周期可能只有几小时（售出即下架）。

人工翻译在这种**无限量、短生命周期**的商品目录上不可能经济可行。LLM 翻译是唯一能让"实时出现的日语商品"在秒级别变成用户可理解内容的方案。设计图中特意定义了 "Translation" 胶囊标签——这不仅是诚实的标注，更是预期管理：告诉用户"翻译可能不完美，但你至少能看懂"。

### 为什么工单而不是在线客服？

这不是 MVP 的"简化"——这是代购业务节奏的**必然选择**。

代购订单的生命周期是"天"级别的：下单 → 人工确认 → 代购 → 日本国内物流 → 国际物流 → 送达。任何一个环节的问题都不可能在实时聊天中解决。在线客服会创造"即时回复"的预期，但代购业务无法兑现这个预期。

工单系统让沟通节奏与业务节奏对齐：用户描述问题 → 运营团队调查 → 给出解决方案。每个步骤都有明确的记录和追踪。工单的结构化数据还为后续流程优化提供了素材——哪些问题最多？哪些环节出问题？这些在碎片化的聊天记录中难以提取。

### 底部五 Tab 的用户生命周期映射

底部导航的五个 Tab 不是随意选择的，它们映射了用户在平台上的完整生命周期：

| Tab | 生命周期阶段 | 角色 |
|-----|------------|------|
| **Home** | 发现（Discovery） | 用户进入平台，浏览和搜索商品 |
| **Favorites** | 考虑（Consideration） | 用户还没下定决心，先收藏 |
| **Cart** | 决策（Decision） | 用户决定要买了，加入购物车准备结算 |
| **Order Link** | 外部导入（External Entry） | 用户从外部渠道带着明确目标进来 |
| **Wallet** | 资金与履约（Fulfillment） | 用户付了钱，关注订单状态和资金 |

这五个 Tab 形成一个完整闭环：从"发现"到"拥有"，用户的每一步都有对应的 Tab 承接。没有多余的 Tab，也没有遗漏的环节。

## 3. Core Business Model

### 聚合代购模式

Rakutao 聚合日本多个电商平台的商品数据，在 Rakutao App 内以统一的商品卡片形式展示。用户在 Rakutao 完成下单和支付后，由 Rakutao 后台在日本源平台代为购买，并统一安排国际物流发往用户收货地址。

**数据来源平台**（设计图"指定购买"页面底部显示）：
- Mercari（メルカリ）
- Rakuma（ラクマ）
- TOBU
- GIOO DIY
- Nicol
- netsea
- SuperDelivery
- BEAMS
- 及其他合作站点

### 品牌策略

- **隐藏来源平台**：首页商品列表中不突出显示源平台信息，强化 Rakutao 自有品牌认知
- **统一体验**：所有平台的商品均以 Rakutao 统一的卡片样式、价格格式和翻译风格呈现
- **平台选择引导**：新用户注册后可关联已有的第三方平台账号（如 Mercari），但整体体验以 Rakutao 为主

### 盈利模式

| 收入来源 | 说明 |
|---------|------|
| **代购手续费** | 每笔订单收取一定比例的服务费（包含在商品展示价格中） |
| **汇率差价** | JPY 到用户本币（VND/TWD/USD 等）的兑换差价 |
| **运费差价** | 日本国内运费 + 国际运费的整合定价，获取物流规模化的差价收益 |
| **充值服务** | 用户通过钱包充值，平台可获取资金沉淀收益 |

## 4. MVP Scope

### 4 大核心页面

#### 首页（Home）
- 搜索栏：支持关键词搜索日本商品（自动翻译为日语搜索）
- 通知入口：站内信 + 站外邮件通知
- 平台分类标签：Picks / Home / Brands / Official / 18kin 等分类
- 商品瀑布流列表：展示商品缩略图、价格（JPY）、标签（Free Shipping / New 等）
- 分平台浏览：Mercari、Rakuma 等站点商品分区
- 拍卖专区入口：拍卖商品列表

#### 购物车（Cart）
- 购物车列表：按卖家分组展示，包含商品图片、名称、价格（JPY）
- 价格变动提示：商品价格发生变化时提醒用户
- 售罄状态处理：已下架商品标记 "Sold"，支持 Archive 操作
- 合计与结算：显示总价，支持选择支付方式
- 底部导航栏：Home / Favorites / Cart / Order Link / Wallet

#### 钱包（Wallet）
- 余额展示：以 JPY 为单位显示钱包余额
- 充值功能：支持充值（チャージ）
- 订单列表模块：所有订单 / 已付款 / 收货中 / 已发货 / 已取消，支持时间和状态筛选
- 拍卖列表：拍卖订单独立管理
- 运单详情模块：运单号、物流状态追踪（Fulfilled / Shipment Processing / Receiving 等）
- 流水记录模块：钱包收支明细
- 订单操作：退款申请（Request a Refund）、催促发货（Urge Shipment）、确认收货（Confirm Receipt）、补充付款（Additional Payment）

#### 收藏夹（Favorites）
- 我的收藏（My Favorites）：已收藏商品列表，显示价格和售罄状态
- 关注卖家（Follow Seller）：关注的店铺列表
- 批量管理：全选、编辑、删除操作
- Sale 状态标记：收藏商品的促销标签

### 指定购买（Order Link）
- 输入商品链接或商品 ID，由平台人工确认价格后代购
- 用户可附加备注说明特殊需求
- 流程：输入链接 → 平台确认价格 → 用户付款 → 平台代购
- 底部展示支持的平台列表（Mercari、TOBU、Nicol、netsea、SuperDelivery、BEAMS 等）

### 搜索与翻译流程
1. 用户输入搜索关键词（英语/繁中/日语）
2. 系统通过 LLM 将非日语关键词翻译为日语
3. 在各源平台执行搜索（爬虫/API）
4. 汇总结果，翻译商品标题和描述为用户语言
5. 以 Rakutao 统一样式展示搜索结果

### 商品详情页
- 商品大图轮播
- 价格展示：JPY 原价 + 汇率换算参考价
- 规格选择（Variant Selection）
- 运费信息：日本国内运费 + 国际运费（按重量计算）
- 卖家信息（隐藏源平台品牌）
- 商品属性：品牌、分类、产地、发货时间、物流方式、尺寸等
- 商品详情描述（LLM 翻译）
- 推荐商品列表
- 操作：加入购物车 / 立即购买

### 用户系统
- 注册/登录：邮箱密码 + 社交登录（Apple / Google / X / Facebook）
- 平台账号关联：可绑定 Mercari 等第三方账号
- 个人中心：头像、昵称、生日、性别、邮箱绑定
- 收货地址管理

## 5. Legal & Compliance Constraints

### 日本主体上架
- Rakutao 以**日本法人实体**为 App Store / Google Play 的上架主体
- 遵守日本《特定商取引法》相关规定
- 所售商品必须为日本境内合法销售的商品

### 注册条款与免责
- 用户注册时必须勾选同意 Rakutao 的 **Terms of Use** 和 **Privacy Policy**（登录页面已设计勾选框）
- 免责声明需涵盖：代购服务性质说明、商品质量由源平台卖家负责、汇率波动风险、物流延误免责等

### 大陆地区屏蔽
- 中国大陆地区 App Store / Google Play 无法下载该应用
- 需在技术层面进行地区限制（IP 检测 + 应用商店地区设置）

### 合法商品限制
- 仅可销售日本境内合法的商品
- 禁止代购违禁品、管制品、仿冒品
- 需建立商品审核机制，过滤不合规商品

## 6. Localization Strategy

### 语言支持

| 语言 | 优先级 | 说明 |
|------|--------|------|
| 日本語 | 默认语言 | App 默认语言，符合日本主体要求 |
| 繁體中文 | 高 | 台湾及港澳用户 |
| English | 高 | 越南及东南亚用户通用语言 |

- 启动页后用户首先进入语言选择页面（设计图 01 语言选择），可选择 繁體中文 / 日本語 / English
- 语言设置可在个人中心（Language Settings）随时切换

### 商品翻译策略
- **实时 LLM 翻译**：用户搜索时，将关键词翻译为日语发起搜索；搜索结果和商品详情使用 LLM 翻译为用户所选语言
- **翻译标识**：翻译后的内容添加"Translation"胶囊标签（设计图组件规范中已定义该标签），提醒用户内容为机器翻译
- **缓存策略**：已翻译的商品信息进行缓存，减少重复翻译成本
- **UI 文案**：App 界面固定文案采用 i18n 国际化方案，三语全量覆盖

## 8. Risks & Constraints

### 技术风险

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| **爬虫稳定性** | 源平台反爬策略升级可能导致商品数据抓取中断 | 多源冗余、定期维护爬虫、监控报警机制 |
| **LLM 翻译成本与延迟** | 大量商品实时翻译产生高额 API 费用，翻译延迟影响用户体验 | 翻译结果缓存、批量翻译优化、关键字段优先翻译 |
| **各平台 API/爬虫合规** | 部分平台 ToS 禁止爬虫或非授权 API 调用，存在法律风险 | 优先对接官方 API、研究各平台 ToS、准备替代数据源 |

### 业务风险

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| **东南亚支付接入复杂度** | 越南、台湾等地支付方式碎片化（银行转账、电子钱包、信用卡等） | 分阶段接入，MVP 先支持主流国际支付 + 钱包充值 |
| **汇率波动** | JPY 兑各币种波动影响用户支付意愿和平台利润 | 实时汇率更新、设置合理汇率保护机制 |
| **物流时效** | 国际物流不确定性高，用户投诉多 | 提供运单追踪、预估时效提示、明确免责条款 |
| **商品侵权/违禁品** | 代购仿冒品或违禁品导致法律纠纷 | 商品审核机制、禁售品类清单、用户举报通道 |

### 运营风险

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| **客服压力** | 仅邮件+工单模式，响应速度可能不满足用户预期 | 建立 FAQ、优化工单分类和自动回复、监控响应时效 |
| **源平台账号管理** | 大量代购操作可能导致 Mercari 等平台账号被封 | 分散账号、控制操作频率、多账号轮换 |
